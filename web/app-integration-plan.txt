PROJECT VISION: THE TTRPG CONTROLLER
The Problem: Traditional Virtual Tabletop (VTT) software treats TTRPGs like filing cabinets or PDF readers. They are data repositories, not interfaces.
The Solution: The human mind is the game engine; we are building the controller. This is a desktop-class digital tabletop engine designed to completely eliminate friction. The goal is that a player can sit down for the first time and play an entire campaign without ever opening a physical rulebook, and a Game Master (GM) can run an entire session without manually looking up a rule.

Core Design Principles
The Mirror Principle: Every AI feature must have a flawless, fully realized manual equivalent. AI is an opt-in speed multiplier, never a crutch. If a user disables all AI, they still have a premium, complete software product.

Privacy by Architecture: The app is structurally incapable of collecting user data. All AI inference runs locally. No API keys, no cloud processing, no training data collection.

Frictionless Client Play: Players should not have to pay, download heavy software, or manage servers to play in their friend's game.

Marketplace as Convenience, Not Utility: Every paid item sits on top of a complete, fully-functional base experience — the marketplace accelerates or personalizes, it never gatekeeps functionality. Sibling to the Mirror Principle: that one draws this line for AI (manual path always complete), this one draws it for monetization (free path always complete). Already the shape of the DLC Ecosystem below (a free/text version of every module always exists; money buys the app-ready convenience of it) — stated here as a general rule so future features default to following it instead of re-deriving it each time.

MONETIZATION & DISTRIBUTION STRATEGY
The ecosystem is designed to maximize player adoption while monetizing the most invested users (GMs) through convenience, and players through deep visual customization.

1. The Host-Client Model
The GM App (Paid): The GM purchases the heavy, standalone desktop engine (a one-time purchase). The GM runs this locally and acts as the host server for the table.

The Player App (Free): Players connect to the GM's local host via a standard web browser on their phone, tablet, or laptop. They get full access to the rules, character creation, and the Command Center UI.

2. Player Premium (The "Game Juice" Upgrade)
Players can optionally purchase a premium client upgrade. This provides zero mechanical advantages. It monetizes identity and visual feedback.

Dynamic Avatars: A modular paper-doll avatar system that visually reflects the character's equipped gear and current state (e.g., looks battered at low HP).
Far-horizon evolution of this: a real parametric character creator (Cyberpunk 2077 / Black Desert-style sliders and components, not an AI-generated image) replaces the flat paper-doll long-term. One built character asset drives both the portrait and the rigged battle-map model described under Far-Horizon Vision below — same identity, two renders. New races and appearance modifiers (hairstyles, body options, cosmetic items) become the sellable content here, following the Marketplace-as-Convenience principle above: the base creator and its default options ship included; new races/modifiers are the optional purchase, purely cosmetic, same zero-mechanical-advantage rule already governing this whole section.

Custom VFX Overlays: Screen-shake effects, custom critical hit animations, and thematic screen borders that react to damage types (e.g., frost crawls the screen on taking ice damage).

Advanced Analytics: Lifetime character performance stats, dice probability audits, and unlimited active character slots.

3. The DLC Ecosystem
We provide the base game rules and a starter adventure for free. Moving forward, we sell premium adventure modules and settings. While users can buy a cheaper text-only version online, the "App Ready" DLC instantly populates the GM's Encounter Builder, Compendium, and NPC Manager, selling the GM their prep time back.

TECHNICAL ARCHITECTURE
The project is moving from a browser-only application to a standalone desktop application for the GM to enable seamless local LLM execution, robust file system access, and stable networking.

Application Framework: Electron (Node.js backend, TypeScript/HTML/CSS frontend). This allows for isomorphic TypeScript—sharing data interfaces directly between the UI, the local database, and network payloads.

Networking: A Node.js web server or WebSockets running inside the GM's Electron app. Browser-based players connect directly to the GM's IP.
Networking Scope Rule: v1 is IN-PERSON-FIRST (LAN / phone hotspot — how most tables actually play: physically together, phones out). Internet play is a follow-up (Phase 6.5) via either a bundled tunnel or WebRTC with a tiny stateless signaling server. A signaling server does not violate Privacy by Architecture — it only brokers the handshake; no game data ever transits it. This decision must be made before Phase 6 begins; it changes the architecture. (NAT traversal / port forwarding is the #1 support nightmare of every self-hosted VTT — do not inherit it casually.)

AI Integration: node-llama-cpp to run .gguf models directly from the local file system. Voice transcription: see Phase 7b — Vosk (default, small offline model) with Whisper as a still-undecided opt-in tier, not a settled single-model choice.
AI Hardware Rule: local LLM quality varies wildly by GM hardware. Ship a small default model, allow bring-your-own .gguf, and let the Mirror Principle absorb every failure gracefully — the manual path is always complete.

Data Structure: All campaigns, encounters, and character data are stored and parsed as clean local JSON files.
Schema Rule: freeze versioned v1 schemas EARLY (character, encounter, compendium entry, lore web) with explicit version fields, shared as isomorphic TS interfaces across UI, database, and network payloads. Phase 6 (network), Phase 9 (DLC ingestion), and the Lore Web all consume the same data — without schema discipline now, three incompatible dialects grow.
System-Agnostic Rule: all schemas are system-agnostic. FROGS 5 / Skyrim is reference content, never hardcoded — the engine must accept any ruleset and any setting (original IP flagship, licensed modules later).

THE PLAYER EXPERIENCE (CLIENT)
The player interface abandons the spreadsheet-style character sheet in favor of a video-game-style Command Center. It organizes data by intent (what can I do right now?) rather than category (what are all my stats?).

The 4-Column Command Center: Weapons, Tactics, Magic, and Items are immediately accessible.

Limited-Use Tracking: Per-combat and per-adventure abilities are tracked end-to-end. Turning on an ability in the portal writes to the local state, and rests automatically clear or preserve used-this-combat states.

Equipment Enchantments: Charge-based active enchantments attach to any equipment item, dynamically tracking depletion and soul-gem recharging.

THE GM EXPERIENCE (HOST)
The GM interface is a campaign-aware session co-pilot. It handles the math and rules so the GM can handle the story.

Universal Compendium: A searchable, inline index of all game content, accessible via a single keystroke without leaving the combat tracker.

Encounter Composer: Pre-build, scale, and save encounters. One click loads all enemies into the combat tracker.

Interactive Lore Web: A physics-driven node graph connecting NPCs, locations, and secrets. It auto-aggregates lexical connections from raw notes and allows the GM to author canonical links seamlessly. (Working prototype exists: the Frogs-5-skyrim repo's _build_web.py scanner + web.html viewer v1.3 — settle-and-freeze physics, drag-to-pin curation layer, candidates engine, secrets matrix.)
THE FLYWHEEL (the moat — state it everywhere): AI session notes (Phase 7) become corpus, and the Lore Web scans corpus — so the graph grows from ACTUAL PLAY automatically. Prep feeds the graph, play feeds the notes, notes feed the graph, the graph feeds next session's prep. No competitor closes this loop.

Passive AI (Keyword Surfacing): As the GM types (or as the local Whisper model transcribes the GM's speech), the system matches keywords against the compendium and silently pops up reference cards for rules, spells, or monster stats on the edge of the screen.

Active AI (Session Notes): At the end of a session, a local LLM can parse the raw transcript and generate a structured draft of the session's combat events, story beats, and NPC interactions for the GM to edit and save.

FAR-HORIZON VISION (well beyond the current roadmap — recorded now so it doesn't get lost, not scoped or scheduled)

A full tactical battlemap staging area for combat, evolving out of the existing combat tracker: real positioning, and procedural animations played on player models for actions taken. Rendering approach: dithering and parallax to fake 3D depth and scene composition while keeping a 2D pixel-art look — high-fidelity, not chibi-stylized, so it reads as the actual character, not a generic sprite. Purpose: let remote play (Discord, etc.) be as tactically alive as sitting at the table together, not to replace in-person play.

Explicitly reconciled against this doc's own opening thesis ("the human mind is the game engine; we are building the controller," rejecting VTTs as passive data repositories): this stays consistent because it is (1) fully opt-in and unnecessary for play, (2) a builder the GM authors with — chosen aesthetic, chosen level of detail, never premade scenes — not a content repository, (3) driven by the same character/combat state the app already tracks and visualizes (the existing combat tracker already mediates combat through HP/FP/turn-order UI; this extends that precedent rather than introducing a new one), and (4) built on the parametric character creator above, so what's on the stage is still the player's own authored choice, not the app deciding anything for them.

Vector-based GM-authored environments, with asset packs sold per DLC/module (same DLC Ecosystem pattern as adventure modules — pre-authored content a GM assembles) and an option to import custom textures/models for GMs who want to go further.
